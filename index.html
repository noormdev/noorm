The problems you stop having

A test database replays the whole migration history before the first test runs.

It builds from the current files in one command.

noorm run build

A stored procedure was hotfixed in a SQL editor, and nobody can say which version is live.

Procedures, views, and functions re-run through a change. History records who ran it, when, and the error if it failed.

noorm change history

A password or API key the database needs sits in a SQL file in git.

Store it encrypted with noorm. The template fills it in when the SQL runs, so the committed file holds only the reference.

How it works

Two folders, two commands

Edit the table in db/sql/. Add a change for databases that already exist. Every environment ends up in the same state.

fresh database     db/sql/      ── noorm run build ──▶  current
existing database  db/changes/  ── noorm change ff ──▶  current

FAQ

Questions developers ask first

Is this migrations with extra steps?

Your migrations become db/changes/: forward and revert files, tracked and checksummed. db/sql/ sits beside them as the current schema, so a fresh database builds from it without replaying history.

Does it replace my ORM?

It replaces the ORM's schema and migration layer. Query with the typed SDK (Kysely underneath), raw SQL, or the client you already use.

Which databases?

PostgreSQL, MySQL, SQLite, and SQL Server. The CLI is one binary with every driver built in.

What about stored procedures?

Call them from TypeScript with typed parameters and result rows, table-valued parameters included.

Do I need both tools?

No. ignatius reads markdown and never connects to a database, so it works with any stack. noorm runs your SQL whether or not a model exists.

Does ignatius generate the SQL?

No. It shows what you intend to build. Write the SQL yourself or hand the model to your agent; From model to SQL shows how each field maps.

If you write SQL by hand and ship it to more than one environment, start here.
