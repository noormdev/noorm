# pipeline_step

Schema v3 provides this independent pipeline history table. Each declared step belongs to one [[pipeline_run]], and stores its own path, rendered SQL checksum, normalized prerequisites, timing, error, skip reason, status and transaction outcome. It has no [[executions|generic execution]] parent or surrogate step ID. A successful step may later be rolled back, pending, or unknown under a pipeline-wide transaction; neither raw invocation input nor rendered SQL is stored.

## Rules and lifecycle

- `(pipeline_run_id, step_no)` is the primary key; `step_no` is the positive one-based declaration position, not graph execution order or stable identity across manifest edits. The logical alternate key `(pipeline_run_id, name)` enforces exact per-run label uniqueness: case, trailing spaces and Unicode are preserved, not normalized. Different declarations may reference the same file, as 1058 shows.
- MySQL implements that alternate key with `uq_pipeline_step_run_name` on `(pipeline_run_id, name_key)`, where `name_key` is generated as `VARBINARY(1020)` from `CAST(name AS BINARY)` in the `utf8mb4` table. MSSQL uses a persisted computed `VARBINARY(511)` key containing `CONVERT(VARBINARY(510), name) + 0x01`, with `name` stored as `NVARCHAR(255)`. The nonzero terminator makes length significant despite SQL Server's binary zero-padding. These are complete native encodings, not hashes or truncated prefixes; their bytes are not interchangeable across platforms. SQLite and PostgreSQL have no `name_key`. It is an implementation detail, not a second identity or a public result field.
- A manifest without `needs` is linear; one with any `needs` is a graph and every step declares dependencies. The non-null `needs` TEXT stores a JSON array of prerequisite declaration numbers: linear steps snapshot their predecessor, while graph labels are mapped to numbers. Duplicate names, unknown dependencies, self-dependencies, cycles and mixed ordering modes fail preflight. All declarations are prepared before workflow SQL, with paths confined to the selected pipeline folder; only referenced SQL and templates execute.
- Under `pipeline`, accept graphs but serialize eligible steps on one pinned session in one transaction. Under `step`, ready graph steps may execute concurrently in separate transactions and connections, bounded by the configured cap and pool size. Under `none`, graph steps have their own pinned sessions; linear `none` uses one pinned session. Session-local state is shared across steps only under `pipeline` or linear `none`, subject to database rules; `step` does not promise session reuse even when linear.
- Stop scheduling on the first failure, settle already active steps, then mark every unstarted declaration skipped. Earlier committed work remains under `step` or `none`; a failed unmanaged step may itself have partial effects. Skips never mean checksum matches. Timestamps are null until start or resolution; never-started steps have zero duration.
- Under `none`, successful author transaction-control SQL does not prove that its effects committed. Recognized control or autocommit changes make affected and subsequent commit provenance unknown; independently confirmed earlier autocommits remain known. Hidden controls in routines or dynamic SQL are outside bounded recognition.
- Workflow outcomes are buffered and persisted independently of workflow transactions. Pending intent can remain visible after a step has started, so pending timestamps do not prove it was unstarted; the illustrative running snapshots are not a promise of live history updates. A fresh invocation executes its declarations again rather than resuming. Checksums shown are abbreviated to eight characters, not a change in runtime hashing.

Source: `docs/spec/sql-pipelines.md` and `src/core/version/schema/migrations/v3.ts`. Declaration position identifies the audit record even when execution order differs. A step cannot exist without its run: the mandatory foreign key cascades deletion of an inactive run to its steps. The composite primary key and unique `(pipeline_run_id, name)` constraint preserve declaration identity and per-run label uniqueness.
