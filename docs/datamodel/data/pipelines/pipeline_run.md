# pipeline_run

Schema v3 provides this independent pipeline history table. Each admitted invocation owns a new identity and its [[pipeline_step|step evidence]]. No pipeline rows are written to [[change]] or [[executions]]; retention of pipeline history is independent of change history. There is no database registry of definitions: a folder and manifest define the workflow.

## Rules and lifecycle

- `created_at` records admission; `started_at` and `finished_at` are null until execution starts or the run resolves, respectively. Identity, config, invoking version, timing, error, workflow status and transaction outcome are recorded directly here, not projected into generic history.
- Pipeline metadata preserves Unicode: MSSQL uses native Unicode text at the existing widths for slug, executing identity, step label, path and safe text fields; MySQL v3 tables explicitly use `utf8mb4`, independent of the database default. Checksums, enums, version strings and the 64-character ownership key retain their existing representations.
- A manifest checksum identifies the prepared definition, not an applied-state gate. Every fresh invocation starts anew; it never resumes or skips steps because an earlier invocation ran the same files.
- Overlap is allowed by default. `single_run` snapshots the manifest's `singleRun` choice; a caller cannot disable manifest-required protection. A protected run claims `active_key`, the full SHA-256 hex digest of the JSON array `[config_name, slug]`, in the same bookkeeping transaction that inserts pending run and step intent. The nullable alternate-key rule `active_key_unique_when_present` represents coordination uniqueness only while a key is present, not a stable business identity: multiple rows may have null keys. A unique index prevents another protected owner of that key, including while pending; collision rolls back all intent. Unprotected runs use null and may overlap. MSSQL uses a filtered non-null unique index; other dialects' SQL unique semantics permit multiple nulls. Existing [[lock]] uniqueness per config cannot provide this scope. This is not business idempotency: SQL owns domain guards and uniqueness.
- Ownership remains on the run until all workflow SQL and transaction activity has settled, including cleanup after audit failure. Clear it only after comparing both run ID and key; an unknown commit acknowledgement alone does not prove activity is ongoing. There is no TTL, lease, automatic steal or force-unlock API. Recovery requires fencing the worker and independently establishing that its SQL and transactions settled; session IDs are not stored here. In the correct database an administrator locks and compares the exact run ID, config, slug and key in a transaction, preserving known terminal outcomes and marking unresolved outcomes unknown unless established independently. A mismatch makes no mutation. Never delete an active protected run.
- Persist the run and intended steps before workflow transactions; buffer outcomes until workflow activity quiesces and persist audit independently so rollback does not erase it. Pending rows may still be durable intent after SQL has started and cannot establish that any step was unstarted. Finalization may fail or be uncertain. Preserve the original execution error across rollback or cleanup failures and never infer a commit or rollback from pending history. Preflight rejection, denial, contention and dry-run create no run. Neither raw invocation input nor rendered SQL is retained in pipeline history.
- `pending` and `running` are unresolved, `partial` means confirmed effects survive alongside failure, `interrupted` means work stopped before normal completion, and `unknown` means transaction outcome cannot be established. Outcomes `pending`, `committed`, `rolled_back`, `partial`, `no_effects`, and `unknown` express transaction certainty; `no_effects` does not claim a rollback under `none`.
- Under `none`, recognized author-controlled transaction or autocommit changes make affected commit provenance unknown even when SQL executes successfully; preserve earlier independently confirmed autocommits. Successful execution with an unknown transaction outcome is not itself a partial failure. Recognition is bounded and cannot establish effects hidden in routines or dynamic SQL.
- Failure to open an owned workflow pool before any workflow dispatch is known quiescent with no workflow effects: persist the admitted failure and skipped declarations, then compare ownership and release the key. This does not apply when activity may still be running.

Source: `docs/spec/sql-pipelines.md` and `src/core/version/schema/migrations/v3.ts`. The guard prevents overlapping work only; SQL still enforces domain repeatability. Administrators may delete inactive runs, cascading to their steps; pipeline retention does not involve generic change history.
