SDK reference ​

Query a noorm-managed database from TypeScript, and run builds, changes, locks, and the vault from the same context.

bash
npm install @noormdev/sdk kysely pg

Install kysely and your dialect's driver as peers:

DialectDriverInstall
PostgreSQL (postgres)pgnpm install @noormdev/sdk kysely pg
MySQL (mysql)mysql2npm install @noormdev/sdk kysely mysql2
SQL Server (mssql)tediousnpm install @noormdev/sdk kysely tedious
SQLite (sqlite)better-sqlite3npm install @noormdev/sdk kysely better-sqlite3

Kysely is required; install only the driver you use. The SDK bundles Tarn for MySQL and MSSQL pooling, so do not install tarn separately.

Requires Node 22.13 or newer. In CommonJS, load the SDK with const { createContext } = require('@noormdev/sdk'). The CommonJS entry and ESM facade share one runtime, including constructors and noormObserver. The type declarations reference Kysely's ESM types: in CommonJS files compiled with module: node16 or later (node18, node20, nodenext), Kysely types you import there do not match ctx.kysely.

typescript
// scripts/open-orders.ts
import { createContext } from '@noormdev/sdk';

interface OrderToCash {
    sales_order: {
        party_id: number;
        order_no: number;
        placed_at: Date;
        status: string;
    };
}

const ctx = await createContext<OrderToCash>({ config: 'dev' });
await ctx.connect();

const applied = await ctx.noorm.changes.ff();

const open = await ctx.kysely
    .selectFrom('sales_order')
    .select(['party_id', 'order_no'])
    .where('status', '=', 'open')
    .execute();

console.log(`${applied.executed} changes applied, ${open.length} open orders`);

await ctx.disconnect();

createContext resolves a config and returns an unconnected Context. connect() opens the pool. changes.ff() applies every pending change and returns a BatchChangeResult. ctx.kysely is a Kysely instance typed by your schema interface. disconnect() closes the pool.

How is a context laid out? ​

Everything on ctx runs SQL. Everything noorm itself does hangs off ctx.noorm:

A context is either connected or not. connect() moves it to connected, disconnect() moves it back, and both are no-ops when already there. Calls that need the pool throw NotConnectedError otherwise:

AreaNeeds connect()Works without it
ctxkysely, transaction, proc, func, tvf, impersonatedialect, connected, withSchema, noorm
runpreview, file, files, dir, builddiscover
changesapply, revert, ff, next, rewind, status, pending, history, historyForChange, getFileHistorycreate, addFile, removeFile, renameFile, reorderFiles, delete, discover, parse, validate
db, lock, dtevery methodnone
vaultevery method except copycopy
transfernoneto and plan open their own connections to both configs
secrets, utilsnoneevery method
templatesnonerender; the vault tier of $.secrets resolves only when connected

Failures arrive as thrown errors, as fields on a result, or as returned data. Error handling lists which call does which. Access policy explains why a call can throw ProtectedConfigError before it touches the database.

The context is not connected when it returns. Connection fields merge in order: built-in defaults, stage, stored config, environment, then connection.

The resolver selects a stored name before considering a synthetic config:

The later layer wins. Three sources can select a stored config, in this order:

That context keeps the stored config's access roles, and keeps its trusted isTest only while the inline fields leave the connection target unchanged. The name is ctx.noorm.config.name and the configName on the context's events and errors. It is also the key for change history, run checksums, locks, pipeline history and local secrets: a database reopened under another name reports its applied changes as pending and runs its build again. Use one name per database.

Neither name nor NOORM_NAME selects a stored config. name with a selected stored config throws Cannot apply the name "<name>" to stored config "<config>", because a stored config's name decides its stage and its protected-stage ceiling. A synthetic config whose name a stored config has throws Cannot name a context "<name>": a stored config is named "<name>", because the context would read and write that config's secrets. This applies to name, to NOORM_NAME, and to the __inline__ and __env__ fallbacks. Select the stored config with config or NOORM_CONFIG=<name>, or use another name. With a stored config selected, NOORM_NAME can rename the context to a name no stored config has; naming another stored config throws An env or flag name cannot rename config "<selected>" to the name of stored config "<name>".

name adds restriction and selects no defaults. Both the name in use and the name it displaced (NOORM_NAME, or the __inline__ or __env__ fallback) are checked:

Stage defaults (isTest: true, access, connection fields) come from the stage option, else from the stage named by NOORM_NAME. A stage named by name supplies none.

Synthetic config names appear in errors and event payloads. With no state file, an inline or environment-only context needs no .noorm/ directory. Deploying an application covers packaging and pool sizing for that setup.

Stage connection defaults such as host, port, user, ssl, and password merge into connection before environment and inline overrides. ssl combines field by field across layers, and rejectUnauthorized is never inherited: it comes from the highest layer that sets ssl, so a stage rejectUnauthorized: false reaches only a config with no ssl of its own. Combining layers has the rules. Stage isTest is a default, and requireTest checks the final resolved value. Protected stages cap effective permission cells at policy-check time without changing assigned roles. Nothing in connection is saved.

Runtime credentials ​

CreateContextOptions['connection'] is InlineConnection<DialectConnectionConfig>: partial connection settings whose pool is typed for the dialect, plus password?: string | (() => string | Promise<string>), a runtime PostgreSQL SSL verifier, and driver. InlineConnection and DialectConnectionConfig are exported. The internal RuntimeConnectionOptions holds the functions and driver separately from serializable config; it is not a package-root export. Persisted Config.connection.password remains a string.

DialectHow a new physical connection gets its password
PostgreSQLThe SDK hands the function to pg's native password option
MySQLThe Tarn pool awaits the function before creating a mysql2 connection. A string password goes through the same pool
MSSQLKysely's Tarn-backed connection factory awaits the function before creating a tedious connection
SQLiteCallable passwords are rejected by createContext()

The callback runs for physical authentication, including a replacement connection, rather than for each query or pool checkout. Rotating a token does not reauthenticate an existing session. disconnect() closes the SDK-owned pool; connecting again creates a new pool.

Reusing a pooled session does not call the credential provider again:

A runtime callback takes precedence over stored and environment passwords. The SDK removes the shadowed password from ctx.noorm.config.connection, without changing stored state. Functions cannot be supplied through YAML or environment variables and are never persisted.

The connection factory records what the callback throws and connect() rejects with exactly that value, so a provider's error class survives instanceof. This holds for a value that is not an Error too, such as a string or the undefined of a bare Promise.reject(); no login is attempted without a credential. A login the pool makes after connect() has no connect() caller: there, a rejection that is not an object reaches the failing query as an Error with the rejected value as its cause, and an object reaches it unchanged. Provider errors may contain secrets. Sanitize them before logging in application code; the fixed event payload does not change the thrown error. A connection with a callback is not retried, because a retry would ask the provider to issue another credential.

TLS certificates ​

A private CA and a client certificate work on PostgreSQL, MySQL and MSSQL. Name each by path and noorm reads the file each time a pool opens, on every connect attempt, so a rotated file needs no new context:

typescript
const ctx = await createContext<DB>({
    config: false,
    name: 'orders',
    projectRoot: '/srv/app',
    connection: {
        dialect: 'mysql',
        host: '10.0.0.5',
        database: 'orders',
        user: 'app',
        tlsServerName: 'db.internal.corp',
        ssl: { caFile: 'certs/corp-ca.pem' },
    },
});
ssl fieldMeaning
ca, cert, keyPEM text
caFile, certFile, keyFilePaths read into ca, cert and key each time a pool opens, on every connect attempt
rejectUnauthorizedfalse encrypts without validating the certificate

One field takes one form: ca with caFile fails with ssl.ca and ssl.caFile cannot both be set; use one. A relative path resolves from projectRoot, a leading ~/ from the home directory, and an absolute path is used as written.

A path that is not a readable regular file, or is empty, over 1 MiB, or holds no PEM block, rejects connect() with SslFileError, which carries field, path and code and never file content. connect() does not retry it, and connection:error carries its message.

typescript
import { attempt } from '@logosdx/utils';
import { SslFileError } from '@noormdev/sdk';

const [, err] = await attempt(() => ctx.connect());

if (err instanceof SslFileError) console.error(err.field, err.path, err.code);

Per-dialect behavior, tlsServerName rules, error hints and how stage, stored, environment and inline ssl combine are in the certificate reference.

PostgreSQL TLS identity ​

For PostgreSQL through an IP host, set ssl: { caFile } (or ca) and tlsServerName to the certificate's DNS identity. The CA validates the chain and the name validates the peer identity. On IP hosts the name also supplies SNI. For DNS dial hosts pg replaces SNI with the dial host, but noorm still verifies the configured name; select a dial host whose SNI reaches the intended certificate. Without tlsServerName, pg and Node use their normal host behavior. tlsServerName and the runtime checkServerIdentity callback need ssl on and certificate validation, and are rejected with rejectUnauthorized: false.

Inline SSL objects may provide checkServerIdentity(hostname, certificate) at runtime. It receives the configured TLS name when present, otherwise Node's hostname, and the peer certificate. Returning an error rejects the connection. This callback replaces Node's standard identity check and must implement any checks the application requires; it does not replace CA chain verification. It cannot be stored in YAML.

Pool connection failures ​

After connect() succeeds, the pool reports a connection it loses, or cannot open, as connection:error on the process-global noormObserver. The payload is { configName, phase, error } with a fixed error string. Driver messages and error objects are not forwarded to the observer.

phaseDialectsFixed errorEmitted when
idlePostgreSQLPostgreSQL idle pool connection failedAn idle pool client fails
idleMySQLMySQL idle pool connection failedAn established connection that is not checked out fails
checked-outPostgreSQLPostgreSQL checked-out connection failedA checked-out session fails
loginPostgreSQLPostgreSQL pool login failedA physical connect the pool makes after its first successful one fails
loginMySQLMySQL pool login failedSame
loginMSSQLMSSQL pool login failedSame

A failed connect() emits connection:error without phase; Runtime credentials lists that payload.

Idle. The pool removes or discards a failed client before reuse, and the replacement physical connection obtains credentials again. Active query failures reject to their callers and produce no idle event.

Checked-out. This includes pinned connections and transactions waiting for application work. The process stays alive, but the session is lost: subsequent queries on that connection reject, and the pool discards it on release. A replacement connection does not restore session advisory locks or the interrupted transaction.

Login. A pool opens more physical connections as demand grows and as old ones are replaced. When one of those logins fails (an expired credential, a throwing password callback, a server that stopped accepting connections), the query that needed the connection still rejects to its caller with the driver's error. The event exists because the first connect() has already returned, so no connect() caller is left to report the failure.

The options are accepted in a stored config, inline, and from the environment as NOORM_CONNECTION_POOL_<option>. Keep the camelCase of the option in the variable name:

bash

NOORM_CONNECTION_POOL_idleTimeoutMs=30000
NOORM_CONNECTION_POOL_maxLifetimeMs=900000

A key that is not a pool option fails validation with pool.<key> is not a pool option, from any of the three sources. The environment reader lowercases an all-caps segment, so NOORM_CONNECTION_POOL_MAXUSES arrives as maxuses and fails with a message that names NOORM_CONNECTION_POOL_maxUses. MIN and MAX are unaffected.

"Rejected" means the config fails validation with pool.<option> is not supported on <dialect>, whichever of the three sources supplied it. The inline type is narrower still: connection.pool is typed per dialect (PgPoolOpts, MysqlPoolOpts, MssqlPoolOpts, and min and max only for SQLite), so an unsupported option on an inline connection with a literal dialect is a compile error first. Each connected context owns a separate pool, so pool maxima are per context, not process-wide.

Driver options ​

connection.driver passes options noorm does not model to the database driver. It is inline only: no environment variable or YAML field sets it, and noorm does not store it, add it to the resolved config, or put it in its own events. A driver that rejects a value can quote it in its error, and that error is the connect() failure and the connection:error text: driver: { charset: 'X' } on MySQL fails with Unknown charset 'X'.

        host: 'db.example.com',

        user: 'app',

Lifecycle ​

typescript
await ctx.connect();

// Fail fast on an unreachable database.
await ctx.connect({ retries: 1, delay: 0 });

connect(retryOptions?) takes ConnectionRetryOptions, exported as a type:

FieldDefaultMeaning
retries3Attempts before giving up
delay1000Milliseconds before the first retry
backoff2Multiplier applied to the delay on each retry

For connections with runtime password callbacks, see Runtime credentials. Static-credential connections retry only messages containing econnrefused, etimedout, too many connections, or connection reset. Authentication, password, login, access-denied, missing-database, and missing-driver errors fail on the first attempt. After the last attempt, the factory throws the last error, as a DatabaseConnectionError where it can explain it.

disconnect() releases any impersonation scope you never reverted, destroys the pool, and clears the connection. Calling it while disconnected is a no-op. A disconnected context can connect() again.

Transactions ​

transaction(fn) hands fn a Kysely Transaction<DB> with proc, func, and tvf attached, and resolves with its return value. A throw inside fn rolls back, so do not swallow errors in the callback.

typescript
const cancelled = await ctx.transaction(async (trx) => {
    const open = await trx
        .selectFrom('sales_order')
        .select('order_no')
        .where('party_id', '=', 2)
        .where('status', '=', 'open')
        .execute();

    await trx
        .updateTable('sales_order')
        .set({ status: 'cancelled' })
        .where('party_id', '=', 2)
        .where('status', '=', 'open')
        .execute();

    return open.length;
});

Routine calls run on the transaction's connection, so they see transaction-scoped settings and roll back with the rest of fn.

typescript
import { sql } from 'kysely';

const open = await ctx.transaction(async (trx) => {
    await sql`SET LOCAL statement_timeout = '8s'`.execute(trx);

    return trx.tvf('party_open_orders', { party_id: 2 });
});
// SELECT * FROM "party_open_orders"("party_id" => $1), cancelled if it runs past 8 seconds
RuleBehavior
Handle typeTransactionScope is Transaction<DB> & RoutineCalls<Procs, Funcs, Tvfs>. A callback annotated (trx: Transaction<DB>) => … still compiles
SET LOCALPostgres syntax. It lasts until the transaction ends

trx.proc on postgresLooks the name up in pg_catalog.pg_proc first: a procedure runs CALL, anything else runs SELECT * FROM name(...). No CALL is attempted against a name with no visible procedure, so calling a function does not abort the transaction. A name that is both a procedure and a function runs CALL, which fails with 42809 and aborts the transaction when it resolves to the function: arguments that match a function overload, or a function earlier on search_path than the procedure. trx.tvf reaches the function in every case

Pinned connections ​

withConnection(fn) pins one pooled connection for the duration of fn and resolves with its return value. fn receives a Kysely<DB> bound to that connection and a PinnedConnection handle. Use it for work that must stay on one session, such as a session-level advisory lock.

connection.discard() marks the connection. When fn ends, the SDK closes the physical connection, and the pool opens a new one on demand. Closing it ends the server session, which releases any session-level locks it held.

typescript
import { sql } from 'kysely';
import { attempt } from '@logosdx/utils';

await ctx.withConnection(async (db, connection) => {
    await sql`select pg_advisory_lock(${lockKey})`.execute(db);

    const [, err] = await attempt(() => syncPrices(db));

    if (err) {
        connection.discard();
        throw err;
    }

    await sql`select pg_advisory_unlock(${lockKey})`.execute(db);
});

Stored procedures, functions and TVFs ​

proc(), func(), and tvf() call routines by name, with the SQL built for the active dialect and every value bound as a parameter. They are not gated by access policy. Declare each routine your database defines as an [Args, Return] tuple and pass the maps as generics:

Parameter handling and NULL semantics ​

Every key present in a params object is sent. The SDK never drops a key, and a value of undefined or null is bound as SQL NULL (sql.ts builds one @key = <value> per Object.entries pair, and Kysely's mssql driver binds both as NVarChar NULL).

MSSQL applies a parameter's DEFAULT only when the parameter is omitted from the call. status: undefined against @status text = 'open' sends @status = NULL, overwrites the default, and fails a NOT NULL column.

Table-valued parameters ​

Kysely's driver cannot bind a TVP, so the SDK emits a batch that declares a table variable of your table type, inserts the rows into it, and passes the variable. Every value stays a bound parameter.

import { tvp } from '@noormdev/sdk';

const lines: NewLine[] = [

const [{ order_no }] = await ctx.proc('place_order', {
    party_id: 2,

Access policy ​

Each config grants a role to two channels: access: { user, agent }. Roles include built-in viewer, operator, and admin and project-defined names; agent: false hides the config from agents. The default is { user: 'admin', agent: 'viewer' }. A protected stage caps each effective user cell at the original operator matrix and each agent cell at the original viewer matrix, without changing the assigned role. Access roles covers setting them.

Malformed stored access is preserved and rejected rather than replaced with a fallback role. A human can repair it, or an unresolved role assignment, without deleting the config or its secrets using noorm config repair-access <name> --user <role> --agent <role|false> --yes. Agents cannot use this recovery path; a valid user role must still permit config:write when only the agent role is unresolved.

reset() takes no options and ignores settings.teardown.preserveTables: it rebuilds from db/sql/, so a surviving table would collide with its CREATE TABLE. It works on a database with no tracking tables, because it creates them. Before it drops anything, reset() throws VersionMismatchError on a newer tracking schema and an Error when it cannot read the schema directory. When the rebuild fails the schema is already gone, so reset() throws ResetBuildError, whose result is the failed BatchResult and whose message names the failing file.

Drop order is foreign keys, procedures, functions, views, tables, then types, and mssql truncate disables constraints one table at a time. Teardown internals gives the reasons, and the mssql strategy covers truncate.

Events ​

Core operations emit events on noormObserver, an ObserverEngine<NoormEvents>. It is one process-global bus, not one per context, so a process that creates several contexts sees all of their events on the same stream.

typescript
import { noormObserver } from '@noormdev/sdk';

const stop = noormObserver.on('file:after', (event) => {
    console.log(`${event.filepath}: ${event.status} in ${event.durationMs}ms`);
});

noormObserver.on(/^change:/, ({ event, data }) => console.log(event, data));

stop();

on returns a function that removes the listener, and a regular expression subscribes to every matching event. Start the process with NOORM_DEBUG=1 to log each event name to stderr.

Error handling ​

A call either returns its value or throws a named, instanceof-matchable error. There are no [value, error] tuples on this surface. Wrap a call in attempt() from @logosdx/utils only to translate, recover, or observe the error; otherwise let it propagate. These calls report differently:

CallReports

vault.get, vault.getAll, vault.initnull, {}, and null for missing access or an existing vault
transaction(fn)fn must throw to roll back
ctx.kysely queriesWhatever the driver throws

import { attempt } from '@logosdx/utils';
import { createContext, RequireTestError, ProtectedConfigError } from '@noormdev/sdk';

const [ctx, err] = await attempt(() => createContext({ config: 'prod', requireTest: true }));

    console.error(`${err.configName} is not a test database`);
}

    console.error(`Denied ${wipeErr.operation} on ${wipeErr.configName}`);
